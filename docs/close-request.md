# 显式请求关闭环境

当 backend 或 resolver 正等待其他线程返回时，那个线程不能同步等待同一环境的 `close()`：
正在进行的安装或替换可能仍持有环境锁。`environment.requestClose()` 提供一个可选的关闭
请求：它只原子设置标记，不取得环境或注册监视器，不调用 backend，也不创建线程。
重复请求无害；`isCloseRequested()` 只观察这个标记。

```java
// 在不应等待清理完成的回调线程中：
environment.requestClose();
// 返回给等待此回调的 backend；不要在这里等待环境关闭。

// 由调用方安排在独立的后台协调步骤中执行，并自行观察该步骤的完成或异常：
environment.close();
```

这两个步骤可能运行在不同线程。调用方必须保证协调步骤不会被等待它的 backend 回调同步等待；
若使用执行器，须确认它不会在回调线程内联执行关闭。SDK 不自动安排、重试或等待协调步骤，
因此只请求而不继续调用 `close()` 会一直留下待清理的环境。正常的 `close()` 一旦通过既有
重入检查并认领关闭，也会设置请求标记。

当请求先于准入检查被观察到时，新安装、接管和替换返回 `TEMPORARILY_UNAVAILABLE`；有效
描述符的并发预解析在检查中观察到请求时返回 `CLOSED`。若预解析已通过最后一次发布检查，
即使请求随后发生，它仍可能返回 `READY`；令牌提交会重新检查，尚未通过提交门禁的令牌会被
消费并返回未安装回执。`CLOSED` 在这里包括“只收到请求”，不代表已调用 `close()` 或完成
卸载。无效参数仍按原有输入检查处理；非描述符目标仍不是预解析支持的目标。

普通安装和替换在检查请求前仍要获取环境监视器并调用 `backend.id()`；请求不会让这些调用
立即返回，也不保证它们未开始外部操作。只有 `requestClose()` 和 `isCloseRequested()` 本身
不等待环境或注册监视器。

在请求与准入检查竞争时，已越过门禁的事务继续按原合同完成：它可能成功安装或替换，也可能
失败并保留未决状态。请求不会撤销其返回的回执或 handle；后续同步 `close()` 负责处理环境
已知的注册。请求后原有 Hook 的回调仍可能执行，已进入调用也不会中断；只有实际关闭注册后
才适用原有的停止接收与在途合同。

调用方可用自己持有的 `Future` 或其他协调机制观察后台 `close()` 返回或抛错，但正常返回
不证明所有框架入口都已恢复、物理资源已经释放或宿主调用全部退出。卸载结果未知时仍保留
原有隔离规则，不自动重试。`isCloseRequested()` 不是清理完成标志。

该接口仅帮助主动使用它的调用方避免**为提出请求而等待环境锁**；直接调用同步 `close()`、
等待清理任务，或持有调用方自己的锁形成的等待环仍需调用方处理。此功能属于当前开发源码，
中央仓库已发布的 1.0.0 不含这两个方法。
