# 离线 CPU body 配对实验核验

`verify_cpu_body_experiment.py` 只读取已完成的 balanced-v1 采集目录、实验计划引用的前置 smoke、仓库内固定版本的单侧和配对核验器，以及独立留存的完整目录清单。不会连接设备或修改输入；JSON 只写到标准输出。使用独立可信渠道保存的计划 SHA-256 和清单 SHA-256，以免把现场刚生成的摘要误当成预登记或完整性证明。

该核验器还要求证据根目录包含 `work/evidence/local/physical-clock-collector/collect.py`，并核对
其字节摘要和 `SERIAL` 常量与采集计划一致。该历史辅助脚本可能包含设备标识，不随仓库发布；
调用方必须自行保管对应原件和证据，缺少或不匹配时核验会失败。不要将含设备标识的脚本或采集数据公开。

```powershell
python tools/performance/verify_cpu_body_experiment.py <实验目录> `
  --evidence-root <包含所有输入的根目录> `
  --plan-sha256 <预登记计划的SHA256> `
  --inventory <实验目录之外的清单文件> `
  --inventory-sha256 <独立留存的清单SHA256>
```

计划沿用现有 `schema_version=1, phase=balanced` 格式，不改写计划：要求指定随机种子、4 区组内各含 B01/B02 × A0/A2 四种组合、各组合两次 AB 和两次 BA、独立 pair/run UUID、起始记录、前置 smoke 摘要及采集器和核验器哈希。按原种子重建顺序；计划时间和主机单调时钟均为采集方自报，无法独立证明预登记发生在采集前。完整清单是 `{schema_version: 1, scope: 字符串, files_count: 整数, files: [{path, bytes, sha256}, ...]}`，路径是根目录相对的正斜杠路径，必须逐项覆盖实验目录中的全部普通文件；清单本身位于实验目录之外。每侧原始日志、进程信息、前后设备快照及配对结果必须在采集结果索引中，现有配对核验器重新检查原始字节。

所有输入必须在指定根目录中，拒绝符号链接及 Windows junction/reparse point；逐次读取前后检查文件身份，实验内实际消费的字节与清单摘要绑定，结束前重读并重新哈希全部清单文件。检查路径与打开文件之间并非原子操作，目录和文件没有被持续锁定，因此应在输入静止期间运行。实际边界快照、设备、制品、进程和时钟都是采集方记录，并非对活设备、系统或模块作用范围的认证。该工具仅适配现有 balanced-v1 数据布局，不自动转换其他计划或修复缺失证据。

完整清单绑定每条采集命令记录的字节，并检查连续序号、身份和当前用户观察、daemon maps/stat 与删除标记、32 个测试进程的 PID/UID/start tick、安装文件哈希和停止前后记录。既有记录不包含每条命令实际使用的 serial；本工具检查 serial 观察值和计划固定的 helper 源码声明，但无法由此独立证明每条命令的实际路由。上述内容均为已保存记录，不是实时设备认证。

逐次读取启动前后设备快照、电池温度和热状态；参照现有采集停止规则，边界电池温度超过 42°C 或相对基线升高至少 5°C 时拒绝该记录。边界数据无法证明运行期间没有升温或降频。时钟门槛、探针门槛与性能门槛均明确保持未评估。

每侧结果保留原始日志路径和哈希、所有读数（含预热），以及样本区间、逐进程阶段中位数和零计数。每组列出四对 AB/BA 的 B/A−1 及其中位数、范围；任一配对未解决或任一侧阶段中位数为零时，该阶段整体 `unresolved`，保留四对而不删除零值。`experiment_records_consistent` 只说明记录内部一致；`unresolved`、`incomplete` 和 `invalid` 均不能视作成功（退出码分别为 2、2 和 1）。没有纯回调 CPU、正式 A/A 合格、置信区间或性能门槛结论，`performance_gate` 始终为 `not_evaluated`。
